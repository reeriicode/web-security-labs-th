# CSRF Lab — แล็บฝึกทำความเข้าใจ Cross-Site Request Forgery

> ⚠ **เว็บนี้ตั้งใจเขียนให้มีช่องโหว่** ใช้เรียนรู้บนเครื่องตัวเองเท่านั้น
> ห้ามเอาขึ้นเซิร์ฟเวอร์จริง และห้ามเอาเทคนิคไปลองกับเว็บที่ไม่ได้รับอนุญาต (ผิด พ.ร.บ. คอมพิวเตอร์ฯ)

---

## 1. CSRF คืออะไร

**CSRF (Cross-Site Request Forgery)** หรือ "การปลอมคำขอข้ามเว็บ"
คือการที่แฮกเกอร์ **หลอกให้เบราว์เซอร์ของเหยื่อส่งคำขอไปยังเว็บที่เหยื่อล็อกอินค้างไว้ โดยที่เหยื่อไม่ได้ตั้งใจ**

หัวใจของมันคือพฤติกรรมของเบราว์เซอร์ข้อเดียว:

> **เวลาเบราว์เซอร์ส่ง request ไปที่เว็บไหน มันจะแนบคุกกี้ของเว็บนั้นไปให้อัตโนมัติเสมอ**
> ไม่ว่า request นั้นจะถูกยิงมาจากหน้าเว็บไหนก็ตาม

ลองนึกภาพ:
1. คุณล็อกอินเว็บธนาคารไว้ แล้วไม่ได้ออกจากระบบ (คุกกี้ session ยังอยู่)
2. คุณเผลอเปิดเว็บของแฮกเกอร์ (จากลิงก์ในแชท / โฆษณา / อีเมล)
3. หน้าเว็บแฮกเกอร์มีฟอร์มที่แอบส่งคำสั่ง "โอนเงิน 5,000 ไปบัญชี hacker" ไปที่ธนาคาร
4. เบราว์เซอร์ของคุณแนบคุกกี้ธนาคารไปให้โดยอัตโนมัติ → ธนาคารเห็นว่า "เป็นคุณ" จริง → โอนเงินให้

เหยื่อไม่ต้องกดอะไรเลย แค่เปิดหน้าเว็บก็โดนแล้ว

### CSRF ต่างจาก XSS ยังไง

| | XSS | CSRF |
|---|---|---|
| แฮกเกอร์ทำอะไร | แอบรันโค้ด **ในเว็บเหยื่อ** | หลอกเบราว์เซอร์ **ยิงคำขอไปเว็บเหยื่อ** จากเว็บอื่น |
| อ่านข้อมูลกลับมาได้ไหม | ได้ (เห็นหน้าจอ อ่านคุกกี้ได้) | ไม่ได้ (ยิงอย่างเดียว อ่าน response ข้ามเว็บไม่ได้) |
| อาศัยอะไร | เว็บไม่ escape ข้อมูล | เว็บเชื่อคุกกี้อย่างเดียว ไม่เช็กว่าคำขอมาจากหน้าของตัวเอง |

## 2. วิธีรัน

ต้องมี [Node.js](https://nodejs.org) (เวอร์ชัน 18 ขึ้นไป) **ไม่ต้อง npm install อะไรเลย**

```bash
node server.js
```

แล้วเปิดเบราว์เซอร์ไปที่ <http://localhost:4000>

### โครงสร้างไฟล์

```
CSRF/
├── server.js     ← เซิร์ฟเวอร์ธนาคารจำลอง + หน้าของแฮกเกอร์ทั้งหมด
├── package.json
└── README.md     ← ไฟล์นี้
```

### บัญชีทดสอบ

| บัญชี | รหัสผ่าน | เงินเริ่มต้น | บทบาท |
|---|---|---|---|
| `alice` | `alice123` | 10,000 | เหยื่อ |
| `hacker` | `hacker123` | 0 | แฮกเกอร์ (เงินจะไหลมาที่นี่) |

## 3. ลองโจมตี (แบบมีช่องโหว่)

1. เข้า <http://localhost:4000> แล้วล็อกอินเป็น **alice** (`alice123`) — จะเห็นยอดเงิน 10,000 บาท
2. **อย่าออกจากระบบ** (เลียนแบบคนที่เปิดเว็บธนาคารค้างไว้)
3. คลิก "เปิดหน้าเว็บของแฮกเกอร์" หรือเข้า <http://localhost:4000/evil> ตรงๆ
   - หน้าจะแสร้งทำเป็นเว็บดูหนังฟรี แต่เบื้องหลังมันยิงคำสั่งโอนเงินทันทีที่โหลด
4. กลับไปที่หน้าธนาคาร → **ยอดเงินของ alice ลดลง 5,000 และไปโผล่ที่บัญชี hacker**
   - ใน terminal ที่รันเซิร์ฟเวอร์จะขึ้นข้อความสีแดง `[โอนเงิน] alice -> hacker : 5000`

alice ไม่ได้กดโอนเลย แค่เปิดหน้าเว็บผิดหน้าเดียว เงินก็หายแล้ว

### payload ของแฮกเกอร์หน้าตาเป็นแบบนี้

ในชีวิตจริงหน้าเว็บแฮกเกอร์ (คนละโดเมน) มีแค่ฟอร์มซ่อนไว้ แล้ว submit อัตโนมัติ:

```html
<form id="attack" method="post" action="https://bank.example/transfer">
  <input name="to" value="hacker">
  <input name="amount" value="5000">
</form>
<script>document.getElementById('attack').submit();</script>
```

หรือแบบที่ง่ายกว่านั้น ถ้าเว็บยอมรับการโอนผ่าน GET แค่แปะรูปก็พอ:

```html
<img src="https://bank.example/transfer?to=hacker&amount=1000">
```

เบราว์เซอร์เห็น `<img>` ก็ไป "โหลดรูป" ให้เอง พร้อมแนบคุกกี้ไปด้วย → โอนเงินสำเร็จ
(ลองได้ในแล็บ: ล็อกอิน alice แล้วเปิด `http://localhost:4000/transfer?to=hacker&amount=1000`)

### โค้ดที่มีปัญหา (`server.js`)

```js
// ❌ โอนเงินโดยเช็กแค่ว่า "มีคุกกี้ session" ไม่เช็กว่าคำขอมาจากหน้าของเราจริงไหม
if (p === '/transfer') {
  if (!s) return res.end('ยังไม่ได้ล็อกอิน');
  doTransfer(s.user, form.get('to'), form.get('amount'));  // ทำตามเลย
}
```

ปัญหาคือ เซิร์ฟเวอร์ถือว่า "มีคุกกี้ = เป็นเจ้าของตัวจริงสั่งมา" ซึ่งไม่จริง
เพราะคุกกี้ถูกแนบไปอัตโนมัติแม้คำขอจะมาจากเว็บของแฮกเกอร์

## 4. ลองแบบที่แก้แล้ว (ปลอดภัย)

1. ยังล็อกอินเป็น alice อยู่ เข้าหน้า <http://localhost:4000/safe> (หน้าธนาคารเวอร์ชันปลอดภัย)
2. เปิดหน้าโจมตีเวอร์ชันยิงใส่หน้า safe: <http://localhost:4000/safe/evil>
3. คราวนี้จะขึ้น **❌ โจมตีล้มเหลว: ถูกปฏิเสธ CSRF token ไม่ถูกต้อง** — ยอดเงินไม่ขยับ

### โค้ดที่แก้แล้ว

```js
// ✅ ต้องแนบ CSRF token ที่ตรงกับ session เท่านั้นถึงจะโอนได้
if (p === '/safe/transfer') {
  if (form.get('csrf') !== s.csrf) {
    return res.end('ถูกปฏิเสธ: CSRF token ไม่ถูกต้อง');
  }
  doTransfer(s.user, form.get('to'), form.get('amount'));
}
```

และในฟอร์มของธนาคารเองจะมี token ที่สุ่มขึ้นมาต่อ session ซ่อนอยู่:

```html
<input type="hidden" name="csrf" value="a1b2c3d4...">
```

**ทำไมถึงกันได้:** token นี้สุ่มขึ้นมาและอยู่แค่ในหน้าของธนาคารเท่านั้น
เว็บของแฮกเกอร์ **อ่าน token นี้ไม่ได้** (กฎ Same-Origin Policy ห้ามเว็บหนึ่งอ่านเนื้อหาของอีกเว็บ)
เมื่อเดา token ไม่ได้ ก็แนบมาในฟอร์มปลอมไม่ได้ คำขอจึงถูกปฏิเสธ

## 5. วิธีป้องกัน CSRF

### ✅ 1. CSRF Token (Synchronizer Token) — วิธีหลัก
ใส่ค่าสุ่มลับต่อ session ในทุกฟอร์มที่เปลี่ยนแปลงข้อมูล แล้วเช็กทุกครั้งที่รับคำขอ (แบบในแล็บนี้)
เว็บอื่นอ่าน token ไม่ได้ จึงปลอมคำขอไม่ได้ เฟรมเวิร์กส่วนใหญ่มีให้ใช้ เช่น
`csurf` (Express), `@csrf` (Laravel), `{% csrf_token %}` (Django), Spring Security

### ✅ 2. คุกกี้ SameSite
ตั้งคุกกี้ session เป็น `SameSite=Lax` (ค่าเริ่มต้นของเบราว์เซอร์ยุคใหม่) หรือ `SameSite=Strict`
→ เบราว์เซอร์จะ **ไม่แนบคุกกี้** ไปกับคำขอที่ยิงข้ามเว็บมา (เช่น form POST จากเว็บอื่น) การโจมตีจึงพัง

```
Set-Cookie: bank_session=...; HttpOnly; Secure; SameSite=Lax
```

> **หมายเหตุสำคัญสำหรับแล็บนี้:** ในแล็บ หน้าแฮกเกอร์ (`/evil`) ถูกวางไว้ที่ origin เดียวกับธนาคาร
> เพื่อให้เดโมทำงานได้แน่นอนบนเครื่องเดียว จึงยังไม่โดน SameSite บล็อก
> ในโลกจริงเว็บแฮกเกอร์อยู่คนละโดเมน `SameSite=Lax/Strict` จะช่วยกันได้อีกชั้นหนึ่ง
> ถือเป็นแนวป้องกันที่ควรเปิดคู่กับ CSRF token เสมอ

### ✅ 3. ไม่ใช้ GET สำหรับการเปลี่ยนแปลงข้อมูล
การโอนเงิน/ลบ/แก้ไข ต้องเป็น POST/PUT/DELETE เท่านั้น ห้ามทำผ่าน GET
เพราะ GET ถูกยิงง่ายมากผ่าน `<img>`, `<link>`, URL ธรรมดา
(แล็บนี้จงใจเปิดช่อง GET ไว้ให้เห็นว่าทำไมมันอันตราย)

### ✅ 4. ตรวจ Origin / Referer header (เสริม)
เช็กว่า header `Origin` หรือ `Referer` ของคำขอมาจากโดเมนของเราเองไหม ใช้เป็นชั้นเสริมได้

### ⚠ สิ่งที่ "ไม่ช่วย" กัน CSRF
- **ตรวจว่าล็อกอินอยู่ไหม** — ไม่ช่วย เพราะ CSRF อาศัยว่าเหยื่อล็อกอินอยู่แล้ว
- **ใช้ HTTPS** — ช่วยเรื่องดักฟัง แต่ไม่เกี่ยวกับ CSRF
- **CAPTCHA ทุกหน้า** — กันได้แต่ใช้งานจริงไม่ไหว ใช้ token ดีกว่า

## 6. สรุปสั้นๆ

> **อย่าเชื่อว่า "มีคุกกี้ = เจ้าของตัวจริงสั่งมา"**
> ทุกคำขอที่เปลี่ยนแปลงข้อมูล ต้องพิสูจน์ว่า "มาจากหน้าเว็บของเราเอง" ด้วย CSRF token

Checklist:
- [ ] ทุกฟอร์ม/คำขอที่เปลี่ยนข้อมูล มี CSRF token และตรวจสอบจริง
- [ ] คุกกี้ session ตั้ง `SameSite=Lax` หรือ `Strict` + `HttpOnly` + `Secure`
- [ ] ไม่มี endpoint ที่เปลี่ยนข้อมูลผ่าน GET
- [ ] (เสริม) ตรวจ Origin/Referer
