# Broken Access Control Lab — แล็บฝึก IDOR + Privilege Escalation

> ⚠ **เว็บนี้ตั้งใจเขียนให้มีช่องโหว่** ใช้เรียนรู้บนเครื่องตัวเองเท่านั้น
> ห้ามเอาขึ้นเซิร์ฟเวอร์จริง และห้ามเอาเทคนิคไปลองกับเว็บที่ไม่ได้รับอนุญาต (ผิด พ.ร.บ. คอมพิวเตอร์ฯ)

---

## 1. Broken Access Control คืออะไร

**Access Control** (การควบคุมสิทธิ์การเข้าถึง) คือกฎที่บอกว่า "ใครทำอะไรกับข้อมูลชิ้นไหนได้บ้าง"
เช่น alice ควรเห็นได้แค่คำสั่งซื้อของ alice เอง และหน้าแอดมินควรเปิดได้เฉพาะแอดมิน

**Broken Access Control** คือเมื่อกฎพวกนี้ **บังคับใช้ไม่ครบหรือไม่ได้บังคับใช้เลย** ทำให้ผู้ใช้
เข้าถึงข้อมูล/ฟังก์ชันที่ไม่ควรได้ นี่คือช่องโหว่ที่ **OWASP จัดอันดับเป็นอันดับ 1 ของปี 2021**
(เลื่อนขึ้นมาจากอันดับ 5) เพราะเจอบ่อยมากและพลาดได้ง่าย

ต้นเหตุหลักมีข้อเดียว:

> **เซิร์ฟเวอร์ตรวจแค่ว่า "ล็อกอินแล้วหรือยัง" (authentication)
> แต่ลืมตรวจว่า "คนที่ล็อกอินอยู่ มีสิทธิ์กับของชิ้นนี้ไหม" (authorization)**

แล็บนี้สาธิต 2 รูปแบบที่พบบ่อยที่สุด:

| รูปแบบ | ย่อมาจาก | ปัญหา |
|---|---|---|
| **IDOR** | Insecure Direct Object Reference | อ้างอิงข้อมูลด้วย id ตรงๆ แล้วไม่เช็กความเป็นเจ้าของ เปลี่ยนเลขก็ดูของคนอื่นได้ |
| **Privilege Escalation** | การยกระดับสิทธิ์ | ผู้ใช้ธรรมดาเข้าถึงฟังก์ชันของแอดมินได้ เพราะเซิร์ฟเวอร์ไม่เช็ก role |

### ในโลกจริงเคยเกิดอะไรบ้าง
- เปลี่ยนเลข `?id=` หรือ `/invoice/1001` ใน URL แล้วเห็นใบเสร็จ/ข้อมูลส่วนตัวของลูกค้าคนอื่น
- เรียก API `/api/users/42` ของคนอื่นได้เพราะเช็กแค่ token ว่าล็อกอิน ไม่เช็กว่าเป็นเจ้าของ id 42
- ผู้ใช้ธรรมดาเดา URL `/admin` หรือยิง API แอดมินตรงๆ แล้วทำงานได้ เพราะปุ่มถูกซ่อนแค่ในหน้า UI

## 2. วิธีรัน

ต้องมี [Node.js](https://nodejs.org) (เวอร์ชัน 18 ขึ้นไป) **ไม่ต้อง npm install อะไรเลย**

```bash
node server.js
```

แล้วเปิดเบราว์เซอร์ไปที่ <http://localhost:4100>

เซิร์ฟเวอร์ฟังเฉพาะ `127.0.0.1` คนอื่นในวง LAN เข้าไม่ได้

### โครงสร้างไฟล์

```
Broken-Access-Control/
├── server.js            ← เซิร์ฟเวอร์ทั้งหมด (Lab 1 IDOR + Lab 2 Privilege Escalation)
├── package.json
├── README.md            ← ไฟล์นี้
└── .claude/
    └── launch.json      ← ตั้งค่าให้รันด้วยปุ่ม preview ได้ (พอร์ต 4100)
```

### เส้นทางสำคัญ

| เส้นทาง | ชนิด | อธิบาย |
|---|---|---|
| `/login`, `/logout`, `/dashboard` | ทั่วไป | เข้าสู่ระบบ / ออก / หน้าบัญชีที่ลิงก์ไปคำสั่งซื้อของตัวเอง |
| `/orders/:id` | ⚠ vuln | IDOR — เช็กแค่ล็อกอิน คืนข้อมูลตาม id |
| `/safe/orders/:id` | ✔ safe | เช็กความเป็นเจ้าของ ไม่ใช่เจ้าของ → 403 |
| `/admin` | ⚠ vuln | Privilege Escalation — เช็กแค่ล็อกอิน ไม่เช็ก role |
| `/safe/admin` | ✔ safe | เช็ก `role === 'admin'` ไม่ใช่ → 403 |
| `/reset` | ทั่วไป | รีเซ็ตข้อมูลกลับค่าเริ่มต้น |

### บัญชี / ข้อมูลทดสอบ

| บัญชี | รหัสผ่าน | สิทธิ์ (role) | คำสั่งซื้อของตัวเอง | บทบาทในแล็บ |
|---|---|---|---|---|
| `alice` | `alice123` | user | 101, 102 | ผู้ใช้ธรรมดา (ใช้เป็นผู้โจมตี) |
| `bob` | `bob123` | user | 201, 202 | ผู้ใช้ธรรมดา (เป็นเหยื่อ) |
| `admin` | `admin123` | admin | - | แอดมินตัวจริง |

แต่ละคำสั่งซื้อมี "ข้อมูลลับ" ของเจ้าของ: สินค้า ยอดเงิน **ที่อยู่จัดส่ง และเบอร์โทร**
สังเกตว่าเลข id เรียงกันเดาง่ายมาก (101, 102, 201, 202) — ซึ่งเป็นเรื่องปกติในระบบจริง

## 3. Lab 1 — IDOR (`/orders/:id`)

### สถานการณ์
ร้านค้าออนไลน์ให้ลูกค้าดูคำสั่งซื้อผ่านลิงก์ เช่น `/orders/101`
alice เป็นเจ้าของ 101, 102 ส่วน bob เป็นเจ้าของ 201, 202

### ลองโจมตีทีละขั้น

1. เข้า <http://localhost:4100> แล้ว<a>ล็อกอินเป็น **alice**</a> (`alice123`)
2. ไปที่ <http://localhost:4100/dashboard> จะเห็นคำสั่งซื้อของ alice คือ #101 และ #102
3. เปิดคำสั่งซื้อของตัวเอง <http://localhost:4100/orders/101> — เห็นข้อมูลปกติ
4. **เปลี่ยนเลขใน URL** เป็น <http://localhost:4100/orders/201> (คำสั่งซื้อของ bob)
   หรือกดลิงก์ `#201 (bob)` ในแถบ "ลองเปลี่ยน id" บนหน้าเว็บ
5. 🔴 หน้า vuln **แสดงที่อยู่และเบอร์โทรของ bob ให้ alice เห็นทันที** ทั้งที่ alice ไม่ใช่เจ้าของ
   - ใน terminal จะขึ้นข้อความสีแดง `[IDOR] alice เปิดดูคำสั่งซื้อ #201 ของ bob ได้ (ข้อมูลหลุด!)`
6. ลองวนเลข 202, 102 ดูได้หมดทุกคำสั่งซื้อ — นี่คือการ "แจกข้อมูลลูกค้าทั้งระบบ" โดยแค่ไล่เลข

7. เทียบกับหน้า safe: <http://localhost:4100/safe/orders/201>
   คราวนี้จะขึ้น **⛔ 403 Forbidden** เพราะ 201 ไม่ใช่ของ alice

### โค้ดที่ผิด ❌ (`server.js` ฟังก์ชัน `orderPage`)

```js
// ❌ เช็กแค่ว่า "ล็อกอินแล้ว" (ทำที่ router ก่อนเข้า orderPage)
//    แล้วคืนข้อมูลตาม id ที่ขอมา โดยไม่สนว่าใครเป็นเจ้าของ
const o = db.orders[id];
return renderOrder(id, o);   // ใครล็อกอินอยู่ ก็ดู order ไหนก็ได้
```

### โค้ดที่แก้ ✅

```js
// ✅ ต้องเป็นเจ้าของ order นั้นเท่านั้น (หรือเป็น admin) ไม่งั้นตอบ 403
if (o.owner !== user.username && user.role !== 'admin') {
  return page(..., 403);   // ปฏิเสธ ไม่คืนข้อมูลเลย
}
return renderOrder(id, o);
```

**หัวใจ:** ทุกครั้งที่หยิบข้อมูลจาก id ที่ผู้ใช้ส่งมา ต้องถามว่า
*"ผู้ใช้คนนี้มีสิทธิ์กับของชิ้นนี้ไหม"* ก่อนเสมอ ไม่ใช่แค่ *"ล็อกอินหรือยัง"*

## 4. Lab 2 — Privilege Escalation (`/admin`)

### สถานการณ์
มีหน้าแอดมินที่โชว์ข้อมูลทุกคน (รวมรหัสผ่านและที่อยู่) ควรเปิดได้เฉพาะ `admin`
แต่หน้า vuln เช็กแค่ว่า "ล็อกอินแล้ว" ไม่ได้เช็กว่า role เป็น admin

### ลองโจมตีทีละขั้น

1. ยังล็อกอินเป็น **alice** (ผู้ใช้ธรรมดา) อยู่
2. เปิด <http://localhost:4100/admin> ตรงๆ (เดา URL เอา ไม่มีปุ่มพาไป)
3. 🔴 หน้า vuln **แสดงรายชื่อผู้ใช้ รหัสผ่าน และคำสั่งซื้อของทุกคน** ให้ alice เห็น
   - ใน terminal จะขึ้นข้อความสีแดง `[PRIV-ESC] alice (role=user) เข้าหน้า /admin ได้ ทั้งที่ไม่ใช่แอดมิน!`
4. เทียบกับหน้า safe: <http://localhost:4100/safe/admin>
   จะขึ้น **⛔ 403 Forbidden — ต้องเป็น admin เท่านั้น**
5. ลองออกจากระบบแล้วล็อกอินใหม่เป็น **admin** (`admin123`) → เข้า `/safe/admin` ได้ปกติ

### โค้ดที่ผิด ❌ (`server.js` ฟังก์ชัน `adminPage` + router)

```js
// ที่ router: เช็กแค่ว่ามี session (ล็อกอินแล้ว)
if (p === '/admin') {
  if (!user) return redirect(res, '/login');
  return send(res, 200, adminPage(req, false));   // ใครล็อกอินอยู่ก็เข้าได้หมด
}
```

### โค้ดที่แก้ ✅

```js
// ✅ หน้า safe: ตรวจ role ก่อนแสดงข้อมูล
if (user.role !== 'admin') {
  return page(..., 403);   // ไม่ใช่แอดมิน ปฏิเสธ
}
return renderAdminData();
```

**หัวใจ:** สิทธิ์ของผู้ใช้ (role) ต้องถูกตรวจ **ที่ฝั่งเซิร์ฟเวอร์ทุกครั้ง**
การแค่ "ซ่อนปุ่มไปหน้าแอดมิน" ใน UI ไม่ใช่การป้องกัน เพราะผู้โจมตีพิมพ์ URL เองได้

## 5. วิธีป้องกัน

### ✅ 1. Deny by default (ปฏิเสธไว้ก่อน)
ทุก endpoint ให้ถือว่า "ห้ามเข้า" เป็นค่าเริ่มต้น แล้วค่อยเปิดสิทธิ์เฉพาะที่อนุญาตชัดเจน
เส้นทางสาธารณะ (หน้าแรก, login) เท่านั้นที่เปิดโดยไม่ต้องตรวจ

### ✅ 2. ตรวจ "ความเป็นเจ้าของ" ทุกครั้งที่อ้างอิงด้วย id
อย่าเชื่อ id ที่ผู้ใช้ส่งมา ต้องผูกข้อมูลกับเจ้าของแล้วเทียบกับผู้ที่ล็อกอินเสมอ

```js
const order = db.orders[id];
if (order.owner !== session.user) return res.status(403);
```

หรือดีกว่านั้น: query โดยผูก owner เข้าไปเลย เช่น
`SELECT * FROM orders WHERE id = ? AND owner = ?` ของคนอื่นจะไม่มีทางถูกดึงมา

### ✅ 3. ตรวจ role / permission ที่ฝั่งเซิร์ฟเวอร์
ทุกฟังก์ชันของแอดมินต้องเช็ก `role === 'admin'` (หรือระบบ permission) ที่เซิร์ฟเวอร์
ใช้ middleware กลางเพื่อไม่ให้ลืมเช็กในบาง endpoint

### ✅ 4. ใช้ id ที่เดายาก (ชั้นเสริม ไม่ใช่ทางแก้หลัก)
ใช้ UUID / ค่าสุ่ม แทนเลขเรียง 1,2,3 ช่วยลดการไล่เดา **แต่ไม่ใช่การควบคุมสิทธิ์**
ถ้าเลข/UUID รั่วออกไป ก็ยังต้องมีการตรวจเจ้าของอยู่ดี

### ⚠ สิ่งที่ "ไม่ช่วย" ป้องกัน Broken Access Control

| วิธี | ทำไมไม่ช่วย |
|---|---|
| ซ่อนปุ่ม/ลิงก์ในหน้า UI | ผู้โจมตีพิมพ์ URL หรือยิง API ตรงได้ ไม่ต้องใช้ปุ่ม |
| เช็กสิทธิ์แค่ฝั่ง JavaScript/หน้าเว็บ | ข้ามหน้าเว็บไปยิงเซิร์ฟเวอร์ตรงๆ ได้เลย |
| ใช้ id เป็น UUID อย่างเดียว | ลดการเดา แต่ถ้า id รั่ว ก็ยังเข้าถึงได้ ต้องเช็กเจ้าของอยู่ดี |
| เช็กแค่ว่า "ล็อกอินแล้ว" | นั่นคือ authentication ไม่ใช่ authorization คนละเรื่องกัน |
| ตรวจ role ตอน render เมนู แต่ไม่ตรวจตอนรับคำขอ | เมนูเป็นแค่ความสวยงาม การบังคับใช้จริงต้องอยู่ที่ตอนรับคำขอ |

## 6. สรุปสั้นๆ (จำไว้ข้อเดียวก็ได้)

> **"ล็อกอินแล้ว" ≠ "มีสิทธิ์"**
> ทุกครั้งที่หยิบข้อมูลตาม id หรือเข้าถึงฟังก์ชันพิเศษ ต้องถามที่เซิร์ฟเวอร์ว่า
> *ผู้ใช้คนนี้มีสิทธิ์กับของชิ้นนี้/ฟังก์ชันนี้จริงไหม*

Checklist ก่อนปล่อยเว็บ:

- [ ] ทุก endpoint ตั้งต้นเป็น "ปฏิเสธไว้ก่อน" แล้วค่อยเปิดสิทธิ์เฉพาะที่ตั้งใจ
- [ ] ทุกจุดที่อ้างอิงข้อมูลด้วย id ตรวจความเป็นเจ้าของที่ฝั่งเซิร์ฟเวอร์
- [ ] ทุกฟังก์ชันแอดมิน/สิทธิ์พิเศษ ตรวจ role/permission ที่ฝั่งเซิร์ฟเวอร์ (ไม่ใช่แค่ซ่อนปุ่ม)
- [ ] การควบคุมสิทธิ์รวมศูนย์ (middleware) ไม่กระจายจนลืมบาง endpoint
- [ ] มีการทดสอบด้วยบัญชีสิทธิ์ต่างกัน (เช่น user ลองเข้าของ admin, alice ลองเข้าของ bob)
- [ ] log การพยายามเข้าถึงที่ถูกปฏิเสธ เพื่อตรวจจับการโจมตี
